# BlazOrbit (BOB) User Skill

Reference for an agent that consumes the BlazOrbit component library — i.e. an
agent producing `.razor` markup, `Program.cs` registrations, and CSS overrides
in a Blazor Server or WebAssembly host that has installed the `BlazOrbit` NuGet
package.

This file gives the rules and the mental model. Detailed catalogs live in
`references/`:

- `references/components.md` — every public component, **all** parameters (own + inherited from `BOBComponentBase` / `BOBVariantComponentBase<,>` / `BOBInputComponentBase<,,>` / `BOBDataCollectionBase<,,>` / `InputBase<>`), base class, and `IHas*` interfaces. Auto-regenerated.
- `references/variants.md` — variant types and built-in values. Auto-regenerated.
- `references/icons.md` — full `BOBIconKeys` catalog (UI semantic set, Brands, FileFormats, MaterialIcons*). Auto-regenerated.
- `references/theming.md` — palette + design-token catalog, sizing/density mechanics, data-attributes, z-index scale.
- `references/presets.md` — enums, preset/factory classes, and parameter value types passed to components.
- `references/patterns.md` — small, focused copy-paste snippets per feature.
- `references/recipes.md` — full-page recipes (landing/hero, dashboard, login, signup, contact, pricing, settings).

When in doubt about a parameter name, type, or default, **read the reference
file rather than guess**. `components.md` is generated by reflection over the
compiled assembly, so it captures inherited parameters that hand-written docs
typically miss (e.g. `BOBDataGrid.Items`, `BOBInputText.Disabled`,
`BOBButton.Variant`).

## Mental model

A BlazOrbit component:

1. Always renders a custom HTML element `<bob-component>` as its root.
2. Carries its state on that root as `data-bob-*` attributes (`data-bob-component`, `data-bob-size`, `data-bob-variant`, `data-bob-disabled`, …). The framework rewrites *volatile* attributes (state-driven) on every render via `PatchVolatileAttributes`; stable attributes are written once.
3. Exposes inline overrides as CSS custom properties (`--bob-inline-color`, `--bob-inline-shadow`, `--bob-inline-border-*`, …) emitted by `BOBComponentAttributesBuilder` based on which `IHas*` interfaces the component implements.
4. Reads its visual identity from a layered token system: **palette** (`--palette-*`) + **design tokens** (`--bob-*`) + **per-instance inline vars** (`--bob-inline-*`). Override at any layer.
5. May be a *variant component* (subclass of `BOBVariantComponentBase<TSelf, TVariant>`) — its render template is selected at runtime from a registry indexed by a `Variant` instance.

You almost never need to touch `<bob-component>` directly. Set parameters; the
framework projects them into the right attributes and CSS variables.

## Quick start

### 1. Service registration (`Program.cs`)

```csharp
using BlazOrbit;
using BlazOrbit.Components;

builder.Services.AddBlazOrbit();          // required: services, JS interop, IModalService, IToastService
// builder.Services.AddBlazOrbitVariants(...) // only if you register custom variants — see "Variants"
```

### 2. Imports (`_Imports.razor`)

```razor
@using BlazOrbit
@using BlazOrbit.Components
@using BlazOrbit.Components.Forms
@using BlazOrbit.Components.Layout
@using BlazOrbit.Components.Layout.Services   @* IToastService, IModalService *@
@using BlazOrbit.Core.Css                     @* PaletteColor *@
```

For Blazor WebAssembly hosts, also `@using BlazOrbit.Components.Wasm`. Add
`@using BlazOrbit.Components.Utils` only when you reference `BOBDateTimePattern`
(everything else under `Utils/` declares `@namespace BlazOrbit.Components`).

### 3. Layout (`MainLayout.razor` or `App.razor`)

The simplest path: use `BOBBlazorLayout` as your `MainLayout`. It auto-mounts
`BOBInitializer` (palette cascade + theme JS bootstrap), `BOBModalHost`
(modal/dialog rendering), and `BOBToastHost` (toast rendering):

```razor
@inherits LayoutComponentBase
<BOBBlazorLayout>
    <BOBSidebarLayout>
        <Header>…</Header>
        <Sidebar>…</Sidebar>
        <ChildContent>@Body</ChildContent>
    </BOBSidebarLayout>
</BOBBlazorLayout>
```

If you write your own root layout, you must mount three things yourself:

```razor
<BOBInitializer DefaultTheme="dark">
    @Body
</BOBInitializer>
<BOBModalHost />
<BOBToastHost MaxVisiblePerPosition="5" />
```

`BOBInitializer` **wraps** its children in a `CascadingValue<BOBPalette>` so
descendants can read theme colors. It is not a marker — it must contain the app
content. `DefaultTheme` selects the theme id that JS applies on first load; the
active theme is also held on `<html data-bob-theme="…">`.

### Hosting bootstrap traps

BlazOrbit needs interactivity to mount its theme cascade and JS interop. The
default Blazor templates run **static SSR** at the root and only enable
interactivity per-component, which leaves `BOBInitializer` without a renderer
and ships pages without the palette cascade (you'll see unstyled components,
no theme switch, and a blank `<body>` flash).

**Server template (`App.razor`)** — mark `Routes` and `HeadOutlet` with the
interactive render mode:

```razor
<!DOCTYPE html>
<html lang="en" data-bob-theme="dark">
<head>
    <HeadOutlet @rendermode="InteractiveServer" />
    <link rel="stylesheet" href="_content/BlazOrbit/css/blazorbit.css" />
    <link rel="stylesheet" href="app.css" />
</head>
<body>
    <Routes @rendermode="InteractiveServer" />
    <script src="_framework/blazor.web.js"></script>
</body>
</html>
```

```csharp
// Program.cs (Server)
builder.Services.AddRazorComponents()
                .AddInteractiveServerComponents();
builder.Services.AddBlazOrbit();

// after var app = builder.Build();
app.MapStaticAssets();
app.MapRazorComponents<App>()
   .AddInteractiveServerRenderMode();
```

**WebAssembly template** — register via `WebAssemblyHostBuilder`:

```csharp
// Program.cs (Wasm)
var builder = WebAssemblyHostBuilder.CreateDefault(args);
builder.RootComponents.Add<App>("#app");
builder.RootComponents.Add<HeadOutlet>("head::after");
builder.Services.AddBlazOrbit();
await builder.Build().RunAsync();
```

**SSR-only pages**: if a page genuinely runs static SSR (no interactivity at
all), `BOBInitializer` will render its children but skip the JS bootstrap; no
ripple, no theme switching, no dropdown JS. Use it sparingly and never for
form-heavy pages.

### Stylesheet and JS includes

`AddBlazOrbit()` does not inject `<link>` / `<script>` tags. Reference them
once in the host page (`App.razor` for Server, `wwwroot/index.html` for Wasm):

```html
<link rel="stylesheet" href="_content/BlazOrbit/css/blazorbit.css" />
```

The framework's interop modules are loaded on demand by individual components
via `IJSRuntime.InvokeAsync<IJSObjectReference>("import", "./_content/BlazOrbit/js/<feature>.js")`,
so no manual `<script>` tag is needed for them. If you ship a custom theme or
overrides, link them **after** `blazorbit.css`.

## Golden rules

1. **Root element.** Every BOB component renders `<bob-component>`. Do not replace it; do not put another `<bob-component>` inside a custom variant template.
2. **Spread `ComputedAttributes`.** When you write a custom variant template, set `<bob-component @attributes="@ComputedAttributes">` on the root. Type is `Dictionary<string, object>`.
3. **Computed state vs raw parameter.** Inputs (`BOBInputComponentBase`) expose `IsDisabled`, `IsError`, `IsReadOnly`, `IsRequired` — these fold in cross-cutting state (e.g. `IsDisabled` includes `Loading` for components that implement `IHasLoading`). Components implementing `IHasActive` / `IHasDisabled` expose `IsActive` / `IsDisabled`. There is no `IsFullWidth` or `IsLoading` virtual — read those raw.
4. **Sizing.** Use `BOBSize` (`Small=0.75×`, `Medium=1×`, `Large=1.25×`). Components scale via `calc(<base> * var(--bob-size-multiplier, 1))`.
5. **Density.** Use `BOBDensity` (`Compact=0.75×`, `Standard=1×`, `Comfortable=1.25×`).
6. **Colors.** Pass either a CSS color string, a CSS custom-property reference, or a `PaletteColor.*` static (it has an implicit `string` conversion). Inline overrides land on `--bob-inline-color` / `--bob-inline-background`.
7. **Variants.** Variant-enabled components expose a `Variant` parameter. Built-in values per type live in `references/variants.md`. To register a custom variant template, see *Variants* below — **do not use razor expression `@<…>` inside `Program.cs`**, that's not legal C#.
8. **Icons.** `IconKey` is a struct with no public instances. Always pass an entry from `BOBIconKeys.*` (e.g. `BOBIconKeys.UI.Save`, `BOBIconKeys.MaterialIconsRound.i_palette`).
9. **Form submission.** `BOBButton` does not expose `Type="submit"`. Inside an `EditForm`, submit with a plain `<button type="submit">…</button>` (BlazOrbit form inputs already styled). Track this gap if more idiomatic submit-via-`BOBButton` shows up in a later release.
10. **Async hygiene.** Do not use `ConfigureAwait(false)` inside callbacks or event handlers that touch BOB components — Blazor relies on the SynchronizationContext to marshal back to the renderer. Gate post-await work on `IsDisposed` when subscribing to `NavigationManager.LocationChanged` or holding a `CancellationTokenSource`.

## Component catalog

Full per-component parameter tables → `references/components.md`. High-level grouping:

- **Generic** (`BlazOrbit.Components`)
  Buttons & feedback: `BOBButton`, `BOBBadge`, `BOBNotificationBadge`, `BOBLoadingIndicator`, `BOBTooltip`, `BOBDraggable`, `BOBSvgIcon`, `BOBCodeBlock`.
  Containers: `BOBTabs` + `BOBTab`, `BOBAccordion` + `BOBAccordionItem`, `BOBCarousel` + `BOBCarouselItem`.
  Selection / data: `BOBSelect<T>` (native `<select>` — feed plain `<option>` children via `ChildContent`), `BOBDataGrid<TItem>` + `BOBDataColumn<TItem>`, `BOBDataCards<TItem>`, `BOBTreeMenu<TItem>` + `BOBTreeMenuItem`, `BOBTreeSelector<TItem>` + `BOBTreeSelectorItem`.

- **Forms** (`BlazOrbit.Components.Forms`)
  `BOBInputText`, `BOBInputTextArea`, `BOBInputNumber<T>`, `BOBInputCheckbox<T>`, `BOBInputRadio<T>`, `BOBInputSwitch`, `BOBInputDateTime<T>`, `BOBInputColor`, `BOBInputDropdown<T>`, `BOBInputDropdownTree<TItem,TValue>`, `BOBInputNumberSlider<T>`, `BOBInputRangeSlider<T>`. Presentation switch: `BOBSwitch<T>` (no validation; for non-form on/off UI). Standalone pickers: `BOBDatePicker`, `BOBTimePicker`, `BOBColorPicker`.

> **`BOBSwitch<T>` vs `BOBInputSwitch`** — both render the same on/off control but `BOBInputSwitch` derives from `BOBInputComponentBase<bool,…>` and integrates with `EditForm` (`@bind-Value`, validation, `aria-invalid`); `BOBSwitch<T>` is a presentation component for free-floating on/off UI (settings toggles, header dark-mode flips). Use `BOBInputSwitch` whenever the value is part of an `EditForm` model.

- **Layout** (`BlazOrbit.Components.Layout`)
  Hosts: `BOBBlazorLayout`, `BOBInitializer`, `BOBModalHost`, `BOBToastHost`.
  Surfaces: `BOBCard`, `BOBGrid` + `BOBGridItem`, `BOBFlexStack`, `BOBSidebarLayout`, `BOBStackedLayout`.
  Overlays: `BOBDialog`, `BOBDrawer`. (Both can also be invoked imperatively via `IModalService`.)
  Theme: `BOBThemeSelector`.

- **Utils** (`BlazOrbit.Components.Utils`): `BOBDateTimePattern` (custom date/time mask).

- **Diagnostics** (`BlazOrbit.Components.Diagnostics`, `DEBUG`-only): `BOBPerformanceDashboard`.

> Toasts and modals are service-driven. Consumers do not place `BOBToast` directly; they call `IToastService.ShowAsync<TBody>(…)` and let `BOBToastHost` (mounted by `BOBBlazorLayout`) render it. Same pattern for dialogs/drawers via `IModalService`.

## Decision matrix — which component for X?

When two BOB components solve the same problem at first glance, pick by axis:

| You want… | Use | Skip |
|---|---|---|
| App shell with persistent left/right nav | `BOBSidebarLayout` | `BOBStackedLayout` (top-nav-only apps) |
| App shell with horizontal nav across the top | `BOBStackedLayout` | `BOBSidebarLayout` (sidebar tree apps) |
| Two-column page section | `BOBGrid` + `BOBGridItem` (`Span`/`Md`/`Lg` props, breakpoint-aware) | `BOBFlexStack` (1-D layout, no breakpoint columns) |
| Inline row of buttons / chips | `BOBFlexStack Direction="Row"` | `BOBGrid` (overkill for 1-D) |
| Drop-down selecting a single value (native UX) | `BOBSelect<T>` (uses native `<select>`) | `BOBInputDropdown<T>` (custom popover; heavier) |
| Drop-down with search, multi-select, custom rendering | `BOBInputDropdown<T>` + child `<DropdownOption>` items | `BOBSelect<T>` (no search, no multi) |
| Drop-down picking a node from a tree | `BOBInputDropdownTree<TItem,TValue>` | flat dropdown |
| Tabular list of records with sort/filter/paging | `BOBDataGrid<TItem>` + `BOBDataColumn<TItem>` slots in `<Columns>` | `BOBDataCards<TItem>` (card grid; no column model) |
| Card grid (gallery, products, profiles) | `BOBDataCards<TItem>` with `CardTemplate` | `BOBDataGrid<TItem>` |
| Hierarchical navigation in a sidebar | `BOBTreeMenu<TItem>` | `BOBTreeSelector<TItem>` (selection, not nav) |
| Picking nodes from a tree with checkboxes | `BOBTreeSelector<TItem>` (`SelectionMode`, `ShowCheckboxes`) | `BOBTreeMenu<TItem>` |
| Page-local confirmation dialog | `<BOBDialog @bind-Open="…">` declarative | `IModalService.ShowDialogAsync` |
| Dialog/drawer triggered from non-UI code or returning a result | `IModalService.ShowDialogAsync<TComponent,TResult>` (body implements `IModalContent`) | declarative |
| Brief notification | `IToastService.ShowAsync<TBody>(…, ToastOptions.Default with { Severity = … })` | inline alert (no dismissal flow) |
| Form on/off toggle | `BOBInputSwitch` (`@bind-Value`, validation) | `BOBSwitch<T>` (presentation only) |
| Standalone date/time/color picker (no form) | `BOBDatePicker` / `BOBTimePicker` / `BOBColorPicker` | `BOBInputDateTime<T>` / `BOBInputColor` (form-bound variants) |

## Theming

### Theme activation

The active theme id sits on `<html data-bob-theme="<id>">`. CSS rules of the form
`html[data-bob-theme="dark"] { --palette-…: …; }` apply that theme's palette.
JS interop, kicked off by `BOBInitializer`, sets the attribute on first load and
on theme changes. `BOBThemeSelector` is the prebuilt switcher component;
implement your own with the JS interop or a custom service if you need fancy
flows.

### Palette

The palette is the public color contract. All BOB components consume from it.
Tokens (also exposed in C# via `BlazOrbit.Core.Css.PaletteColor`):

```css
--palette-primary              --palette-primary-contrast
--palette-secondary            --palette-secondary-contrast
--palette-surface              --palette-surface-contrast
--palette-background           --palette-background-contrast
--palette-error                --palette-error-contrast
--palette-success              --palette-success-contrast
--palette-warning              --palette-warning-contrast
--palette-info                 --palette-info-contrast
--palette-border               --palette-shadow
--palette-highlight
```

Override per-theme:

```css
html[data-bob-theme="brand-dark"] {
    --palette-primary:           #5b8def;
    --palette-primary-contrast:  #ffffff;
    --palette-surface:           #1a1d23;
    --palette-surface-contrast:  #f1f3f7;
    /* …etc */
}
```

In C#, pass `PaletteColor.Primary` (or any other static) wherever a parameter
takes a string color — it has an implicit `string` conversion to its
`var(--palette-primary)` form.

### Design tokens (beyond the palette)

The look-and-feel layer below the palette. Override at `:root` (global) or under
a theme selector to scope per theme. Token catalog → `references/theming.md`.
Highlights:

- **Sizing / density multipliers**: `--bob-small-multiplier`, `--bob-medium-multiplier`, `--bob-large-multiplier`, `--bob-compact-multiplier`, `--bob-standard-multiplier`, `--bob-comfortable-multiplier`. Component scales via `calc(<base> * var(--bob-size-multiplier))`.
- **Border / radius defaults**: `--bob-border-width`, `--bob-border-style`, `--bob-border-radius`, plus family-specific (`--bob-input-radius`, `--bob-picker-radius`).
- **Typography**: `--bob-font-family`, `--bob-font-family-heading`, `--bob-font-mono`, `--bob-font-size-base`, `--bob-line-height`, `--bob-line-height-heading`.
- **Focus / outline**: `--bob-highlight-outline`, `--bob-highlight-outline-offset`.
- **Opacity**: `--bob-opacity-disabled`, `--bob-opacity-placeholder`.
- **Z-index scale**: `--bob-z-dropdown` (1000) → `--bob-z-toast` (1500). Stay inside the scale — don't introduce ad-hoc `z-index: 9999`.
- **Ripple / scrollbar / family-specific**: see the reference.

```css
:root {
    /* App-wide token overrides */
    --bob-font-family:        "Inter", system-ui, sans-serif;
    --bob-border-radius:      8px;
    --bob-input-radius:       6px;
}
html[data-bob-theme="brand"] {
    /* Theme-scoped token overrides + palette */
    --bob-highlight-outline:  3px solid var(--palette-primary);
    --palette-primary:        #1f6feb;
}
```

### Inline (per-instance) overrides

For one-off overrides without writing CSS, set the matching parameter — the
framework emits the inline CSS variable on `<bob-component>`:

| Parameter(s) | Inline CSS variable |
|---|---|
| `Color` / `BackgroundColor` | `--bob-inline-color`, `--bob-inline-background` |
| `Border` (`BorderStyle`) | `--bob-inline-border` and side variants, `--bob-inline-border-radius` |
| `Shadow` (`ShadowStyle`) | `--bob-inline-shadow` |
| `RippleColor` / `RippleDurationMs` | `--bob-inline-ripple-color`, `--bob-inline-ripple-duration` |
| `PrefixColor` / `PrefixBackgroundColor` | `--bob-inline-prefix-*` (input family) |
| `SuffixColor` / `SuffixBackgroundColor` | `--bob-inline-suffix-*` (input family) |
| `Elevation` | `--bob-inline-elevation-tint` (cards, drawers) |

## Variants

Variants change the **render template**, not just attributes. The body of a
variant template is real Razor markup, so variant templates **must live in a
`.razor` file** — you cannot inline them as `@<…>` inside `Program.cs`.

Three working patterns, ordered by typical preference:

### A — `RenderFragment<T>` from a Razor template method (most common)

Razor markup is not legal inside `.cs`, so the variant body lives in a
`.razor` file. Use a `RenderFragment` template method (`@{ ... <markup> ... }`)
and expose it as a static `RenderFragment<TComponent>`:

```razor
@* Templates/ButtonTemplates.razor *@
@* No @page / @inherits — this file only declares static templates. *@

@code {
    public static readonly BOBButtonVariant Gradient = BOBButtonVariant.Custom("Gradient");

    public static readonly RenderFragment<BOBButton> GradientTemplate = button => @<text>
        <bob-component @attributes="@button.ComputedAttributes">
            <button type="button"
                    class="transition-target"
                    disabled="@button.IsDisabled"
                    @onclick="async e => await button.OnClick.InvokeAsync(e)"
                    style="background: linear-gradient(135deg, var(--palette-primary), var(--palette-secondary)); color: var(--palette-primary-contrast); border: 0;">
                @button.LeadingIcon?.SvgContent
                @button.Text
            </button>
        </bob-component>
    </text>;
}
```

`@<text>…</text>` is the Razor explicit-template syntax that turns the markup
into a `RenderFragment` while letting you reference the lambda parameter
(`button`). Without `<text>` Razor cannot tell the markup apart from C#.

```csharp
// Program.cs
using MyApp.Templates;

builder.Services.AddBlazOrbitVariants(b =>
{
    b.ForComponent<BOBButton>()
     .AddVariant(ButtonTemplates.Gradient, ButtonTemplates.GradientTemplate);
});
```

```razor
@* Consumption *@
<BOBButton Text="Save" Variant="@ButtonTemplates.Gradient" OnClick="SaveAsync" />
```

Cache the variant instance (`ButtonTemplates.Gradient`) once and reuse it
everywhere — `BOBButtonVariant.Custom("Gradient")` builds a fresh instance per
call but they compare equal by `(Type, Name)`.

### B — Subclass the variant component

When the variant needs additional parameters or behavior (not just markup), subclass:

```razor
@* MyBOBButton.razor *@
@inherits BOBButton

<bob-component @attributes="ComputedAttributes">
    <button @ref="_ref" class="my-custom-btn transition-target"
            disabled="@IsDisabled"
            @onclick="async e => await OnClick.InvokeAsync(e)">
        @ChildContent ?? @Text
    </button>
</bob-component>

@code {
    private ElementReference _ref;
    public override ElementReference GetRippleContainer() => _ref;
}
```

Use `<MyBOBButton …/>` in markup. No DI registration needed — the `.razor`
defines a standalone component that inherits the BOB pipeline.

### C — Inline lambda + factory call (rare)

If the template is trivially short you can inline it, but **the lambda body
still has to be a `RenderFragment`-returning method defined in a `.razor`
file** — Program.cs can only reference it. Treat this as a syntactic variant
of pattern A.

## Forms & validation

`BlazOrbit.Components.Forms` inputs integrate with the standard `EditForm`
pipeline. Wrap inputs in `<EditForm Model="…" OnValidSubmit="…">`, add
`<DataAnnotationsValidator />` (or `BOBFluentValidator` from
`BlazOrbit.FormsFluentValidation` for FluentValidation), use `@bind-Value`.

```razor
<EditForm Model="@_model" OnValidSubmit="HandleValidSubmit">
    <DataAnnotationsValidator />

    <BOBInputText @bind-Value="_model.Name"
                  Label="Full name"
                  HelperText="As it appears on your ID"
                  Required="true"
                  PrefixIcon="@BOBIconKeys.UI.Person" />

    <BOBInputText @bind-Value="_model.Email"
                  Label="Email"
                  Variant="BOBInputVariant.Filled"
                  Color="@PaletteColor.Primary" />

    <button type="submit">Submit</button>
</EditForm>
```

Auto-wired by `BOBInputComponentBase`:

- `IsError` reflects both the explicit `Error` parameter and the cascaded `EditContext` validation messages for the bound field.
- `data-bob-error="true"` and `aria-invalid="true"` are emitted when `IsError` is `true`.
- `aria-required="true"` matches the `Required` parameter; `aria-describedby` is wired to the helper-text/error-text element id.
- The `HelperText` slot is replaced by the validation message when validation fails.

For a richer set including standalone pickers and floated labels, see the
component catalog and `references/patterns.md`.

> **Submit gap**: `BOBButton` has no `Type` parameter. Wrap the styled button
> in a plain `<button type="submit" style="all: unset;">…</button>` inside
> the form so it can both trigger `OnValidSubmit` and keep BlazOrbit styling.
> Alternatively call `EditContext.Validate()` and your submit handler from
> `BOBButton.OnClick`. See `references/recipes.md` for both patterns.

### FluentValidation (optional)

Install `BlazOrbit.FormsFluentValidation` (NuGet — note the `BlazOrbit`
prefix; it would otherwise clash with `FluentValidation` itself). Drop the
`<DataAnnotationsValidator />` and replace with `<BOBFluentValidator />`,
then register your `AbstractValidator<T>` in DI:

```csharp
// Program.cs
builder.Services.AddScoped<IValidator<SignupModel>, SignupModelValidator>();
```

```razor
<EditForm Model="_model" OnValidSubmit="HandleSubmitAsync">
    <BOBFluentValidator />
    <BOBInputText @bind-Value="_model.Email" Label="Email" />
    ...
</EditForm>
```

Errors flow through the same `EditContext` channel, so `IsError` /
`HelperText` slot replacement / `aria-invalid` continue to behave identically.

### Localization (optional)

Two glue packages, one per host:

- `BlazOrbit.Localization.Server` — cookie-backed `RequestLocalization` setup.
- `BlazOrbit.Localization.Wasm` — `localStorage`-backed culture persistence.

Both expose `BOBCultureSelector` (a small dropdown of supported cultures with
flag glyphs). Register in `Program.cs`:

```csharp
using System.Globalization;

// Server
builder.Services.AddBlazOrbitLocalizationServer(options =>
{
    options.SupportedCultures = [new("en"), new("es"), new("de")]; // List<CultureInfo>
    options.DefaultCulture    = "en";
});

// Wasm
builder.Services.AddBlazOrbitLocalizationWasm(options =>
{
    options.SupportedCultures = [new("en"), new("es")];
});
```

```razor
<BOBCultureSelector />
```

The library's own strings travel with `BlazOrbit.Translations`. Your app's
strings stay in your own `.resx` consumed via `IStringLocalizer<T>` as
normal.

## Modals, dialogs, drawers, toasts

Two complementary surfaces:

1. **Inline declarative**: `<BOBDialog @bind-Open="…">` / `<BOBDrawer @bind-Open="…">`. Use when the lifecycle is page-local.
2. **Imperative service**: `IModalService` (dialogs/drawers) and `IToastService` (toasts). Use when invoking from event handlers or non-UI code.

### `IToastService` (verbatim signature)

```csharp
public interface IToastService
{
    event Func<Task>? OnChangeAsync;
    IReadOnlyList<ToastState> ActiveToasts { get; }

    Task CloseAsync(Guid toastId);
    Task CloseAllAsync();
    Task PauseAsync(Guid toastId);
    Task ResumeAsync(Guid toastId);

    Task ShowAsync(Action<RenderTreeBuilder> builder);
    Task ShowAsync(Action<RenderTreeBuilder> builder, ToastOptions? options);
    Task ShowAsync<TComponent>() where TComponent : IComponent;
    Task ShowAsync<TComponent>(ToastOptions? options) where TComponent : IComponent;
    Task ShowAsync<TComponent>(IDictionary<string, object?>? parameters) where TComponent : IComponent;
    Task ShowAsync<TComponent>(IDictionary<string, object?>? parameters, ToastOptions? options) where TComponent : IComponent;
}
```

**There is no `Show(string, severity)` overload.** A toast is always rendered
by a Razor body component (or an explicit `RenderTreeBuilder` action). Pass
severity/position/duration via `ToastOptions`:

```razor
@inject IToastService ToastService

<BOBButton Text="Save" OnClick="SaveAsync" />

@code {
    private async Task SaveAsync()
    {
        await DoWorkAsync();
        await ToastService.ShowAsync<MySuccessToast>(
            new Dictionary<string, object?> { ["Message"] = "Saved!" },
            ToastOptions.Default with { Severity = ToastSeverity.Success });
    }
}
```

`ToastOptions` has prebuilt instances: `Default` (5s, top-right, slide+fade),
`Quick` (2s), `Long` (10s), `Persistent` (no auto-dismiss). Use `with` to tweak.

### `IModalService` (verbatim signature)

```csharp
public interface IModalService
{
    event Func<Task>? OnChangeAsync;
    IReadOnlyList<ModalState> ActiveModals { get; }

    Task CloseAllAsync();
    Task CloseAsync();

    Task<TResult?> ShowDialogAsync<TComponent, TResult>(object? parameters = null, DialogOptions? options = null) where TComponent : IModalContent;
    Task                  ShowDialogAsync<TComponent>(object? parameters = null, DialogOptions? options = null) where TComponent : IModalContent;
    Task<TResult?> ShowDrawerAsync<TComponent, TResult>(object? parameters = null, DrawerOptions? options = null) where TComponent : IModalContent;
    Task                  ShowDrawerAsync<TComponent>(object? parameters = null, DrawerOptions? options = null) where TComponent : IModalContent;
}
```

The dialog/drawer body must implement `IModalContent` so the host can hand it
its close handle. Use `DialogOptions` / `DrawerOptions` for size, position
(drawers), and overlay/escape behavior.

#### `IModalContent` + `ModalReference` — full contract

```csharp
namespace BlazOrbit.Components.Layout;

public interface IModalContent
{
    ModalReference ModalReference { get; set; }
}

public sealed class ModalReference
{
    public string Id { get; }
    public Task CloseAsync();                          // close with no result (returns null)
    public Task CloseAsync<TResult>(TResult result);   // close + supply result for awaiter
}
```

The host **cascades** the `ModalReference` into the body component, so the
property is decorated with `[CascadingParameter]`, not `[Parameter]`:

```razor
@* Dialogs/ConfirmDialog.razor *@
@implements IModalContent

<BOBDialog Open="true" Title="@Title" CloseOnOverlayClick="false">
    <Content>@Message</Content>
    <Footer>
        <BOBButton Text="Cancel" OnClick="() => ModalReference.CloseAsync(false)" />
        <BOBButton Text="Confirm"
                   BackgroundColor="@PaletteColor.Primary"
                   Color="@PaletteColor.PrimaryContrast"
                   OnClick="() => ModalReference.CloseAsync(true)" />
    </Footer>
</BOBDialog>

@code {
    [CascadingParameter] public ModalReference ModalReference { get; set; } = default!;

    [Parameter] public string Title   { get; set; } = "Confirm";
    [Parameter] public string Message { get; set; } = "Are you sure?";
}
```

Caller awaits the result:

```csharp
bool confirmed = await ModalService.ShowDialogAsync<ConfirmDialog, bool>(
    parameters: new { Title = "Delete user", Message = $"Remove {user.Email}?" },
    options: new DialogOptions { MaxWidth = "440px" });

if (confirmed) await DeleteAsync();
```

Notes:

- `parameters` is a plain anonymous object reflected onto the component's
  `[Parameter]` properties. Mismatched property names are silently dropped —
  type carefully.
- The body component's `[CascadingParameter] ModalReference` must be assigned
  before any user action; never read it from `OnInitialized` and assume it's
  populated — wait until `OnAfterRenderAsync(true)` if you need it before user
  interaction.
- `CloseAsync()` (no result) makes the `Task<TResult?>` returned by
  `ShowDialogAsync<TComponent,TResult>` complete with `null`/`default`.
- Nested modals stack; `ActiveModals` exposes the stack in registration order.

### Inline `BOBDialog` (declarative)

```razor
<BOBDialog @bind-Open="_open" Title="Confirm" MaxWidth="480px">
    <Content>
        Are you sure you want to delete @_target.Name?
    </Content>
    <Footer>
        <BOBButton Text="Cancel" OnClick="() => _open = false" />
        <BOBButton Text="Delete"
                   BackgroundColor="@PaletteColor.Error"
                   Color="@PaletteColor.ErrorContrast"
                   OnClick="DeleteAsync" />
    </Footer>
</BOBDialog>
```

`BOBDialog` slots are `Header`, `Content`, `Footer` — **not** `ChildContent` or
`Actions`. `BOBDrawer` uses `Header`, `ChildContent`, `Footer` plus `Position`
(`Left` / `Right` / `Top` / `Bottom`) and `Size`.

## Parameter value types — quick reference

| Where you see it | Type | How to construct / pick |

| `Size`, `Density` | `BOBSize`, `BOBDensity` | enum constants |
| `Color`, `BackgroundColor`, `RippleColor`, `…Color` | `string?` | CSS string, `var(--…)`, or `PaletteColor.<Name>` (implicit string) |
| `Border` | `BorderStyle?` | `BOBBorderPresets.<Name>` (e.g. `Rounded`, `RoundedLarge`, `Subtle`, `Strong`, `Pill`, `Primary`, `Error`) or `BorderStyle.Create().All("2px", BorderStyleType.Solid, PaletteColor.Primary).Radius(8)` fluent |
| `Shadow` | `ShadowStyle?` | `BOBShadowPresets.Elevation(level)` (level 0–24) or `ShadowStyle.Create(y, blur, opacity, x: 0, spread: 0, color: null, inset: false).Add(…)` |
| `Transitions` | `BOBTransitions?` | `BOBTransitionPresets.<Name>` (`HoverScale`, `HoverShadow`, `HoverFade`, `HoverLift`, `CardHover`, `FocusRing`, `Interactive`, `MaterialButton`, `PremiumButton`, `GlassMorphism`, `Neumorphism`) |

| Accordion | `BOBAccordionMode` | enum (`Single`, `SingleStrict`, `Multiple`) |

## Accessibility notes

- Icon-only buttons or inputs **must** set `AriaLabel`. Otherwise screen readers see nothing meaningful.
- Inputs auto-emit `aria-invalid`, `aria-required`, `aria-describedby`. Don't manually duplicate.
- Focus outlines use `var(--bob-highlight-outline)` driven by `--palette-highlight`. Override at `:root` or under `html[data-bob-theme]`.
- Toast severity drives ARIA: `Error` renders `role="alert" aria-live="assertive"`; others use `role="status" aria-live="polite"`.
- In custom variant templates, propagate `IsDisabled` to the inner element's `disabled` attribute and forward `OnClick`.
